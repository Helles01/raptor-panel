# M13 groundwork – backup rules

Status: **groundwork done** (2026-10-22): the rules of backups that need no database. The endpoints (`/servers/{server}/backups*`,
`/api/remote/backups/*`), the calls to Wings and the S3 handling wait for the schema.

## Done: `internal/backups`
| Function | Content |
|---|---|
| `Admit(limit, existing, override)` | May a server start another backup? A server with no limit set (null) or 0 may not have backups at all (as in the reference). At the limit, an `override` (schedules) replaces the **oldest unlocked** backup (ties by id); locked backups are never replaced; if nothing can be replaced the answer is `TooManyError` with the reference's text. Only one is replaced, even for a server over its limit (as the reference). `existing` holds the backups that count: running ones and successful ones, not failed. |
| `Throttle(started, now, limit, period)` | At most `limit` backups started within `period` (the reference: 2 in 600 s; period 0 turns it off). `started` includes deleted and failed backups so delete-and-start-again does not get round it. The error carries the reference's text and the wait for `Retry-After` (`RetryAfterSeconds`). |
| `Name`, `ParseIgnored` | The default name `Backup at <time>`, trimming as PHP's `trim`, and the list of files to leave out (one pattern per line). Bounds and control-character checks (C-027). |
| `State.CanDelete`, `CanRestore`, `CanDownload` | A locked finished backup cannot be deleted (a failed one can); restoring needs a server in its normal state and a finished, successful backup; downloading needs a finished, successful one (C-026). |
| `Complete(current, report)` | What the panel stores when a node reports the end of a backup: a failed one is unlocked, has no checksum and size 0; a successful one gets `type:checksum`, the size and keeps its lock. A backup that is already completed cannot be reported on again (C-026). Checksum type and value are checked against allow-lists. Wings v1.13.4's `backup.go` hard-codes `sha1` with a hex digest; the S3 variant's own file sets no type and hands over to the same function, so it is assumed to send the same. The allow-lists are wider than that (letters, digits and `+ / = _ . -`), to be checked against a real S3 backup in M17. |
| `ValidDisk` | `wings` and `s3`, the two disks the reference knows. |

`internal/schedules` now uses `backups.ParseIgnored` for the payload of a backup task, so a schedule and a manual backup accept
the same lists.

Mutation checks confirmed that each of these fails a test: replacing locked backups, the limit boundary, "no limit means
unlimited", the throttle window edge, the retry computed from the newest, reporting twice, a failed backup keeping its lock,
deleting a locked failed backup, the order of the restore checks, name trimming, and carriage-return handling.

## What matches the reference
The limit rules (null and 0 mean none, replacing the oldest unlocked backup for schedules), the throttle numbers and texts, the
default name, the lock and restore rules, the stored form of a finished backup (`type:checksum`, size, unlock on failure), and the
two disks.

## Deliberate differences (`docs/compat.md`: C-026, C-027)
- A finished backup cannot be reported on again, and only a successful one can be downloaded (C-026).
- Bounded names and ignored-file lists, a `Retry-After` that is the real wait, and a fixed event name for a failed restore (C-027).

## Still to do (waits for the schema)
- **The transaction**: counting, pruning and creating must happen in one transaction with the server's backups locked
  (`SELECT … FOR UPDATE`), otherwise two requests can both see room (plan 10.1 d). `Admit` assumes it.
- The node-ownership check of the remote endpoints: a node may report only on backups of its own servers (structural, M7).
- The backup identifier of the remote endpoints is generated by the panel and format-checked (a UUID).
- Wings calls (create, restore, delete: a 404 from the node on delete is not an error), the S3 multipart handling and signed
  URLs, the 15-minute download token (`wings.Issuer.BackupDownload` exists), the activity events
  (`server:backup.start|complete|fail|lock|unlock|delete|download|restore|restore-complete|restore-failed`), the lock toggle
  (needs `backup.delete`), pagination (`per_page` at most 50), and `backup_count` in the list's meta.
- Locking at creation needs `backup.delete` (the reference ignores `is_locked` from users without it).
